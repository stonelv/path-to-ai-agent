## 1. 本月目标

本月的重点不是构建复杂 Agent，而是掌握可靠调用大模型并将非结构化文本转换成可验证数据的工程方法。

完成本月学习后，应能够：

1. 使用 Python 调用大模型 API，并理解消息、Token、上下文窗口和采样参数。
2. 使用 Pydantic 定义结构化输出，并对模型结果进行严格校验。
3. 实现异步模型调用，理解同步与异步的边界；流式输出作为后续交互扩展。
4. 正确处理超时、限流、网络失败和无效模型输出。
5. 使用 FastAPI 暴露服务接口，并通过 Docker 启动应用。
6. 使用 pytest 建立自动化测试，并建立覆盖关键场景的小型固定评估集。
7. 记录模型名称、请求 ID、Token、延迟和错误类型。
8. 完成一个航司行李额结构化提取程序，并用量化指标验证效果。

建议投入时间：每周 10～15 小时，共 4 周，用于必做闭环；不是保证完成全部进阶内容的期限。
已有工程经验者可通过验收跳过补课。每个项目还需完成一次[AI 编程协作练习](../docs/coding-agent-workflow.md)。

## 2. 月度项目

### 2.1 项目名称

航司行李额结构化提取程序（Airline Baggage Allowance Extractor）

### 2.2 业务背景

航空公司的行李政策通常以自然语言呈现，并受到航司、航线、舱位、会员等级、票价品牌和行李类型等条件影响。程序需要从政策文本、订单说明或客服回复中提取结构化的免费行李额和限制信息。

### 2.3 输入示例

```text
北京至东京经济舱成人旅客可免费托运1件行李，每件不超过23公斤，
三边之和不得超过158厘米。婴儿票可托运1件不超过10公斤的行李。
```

### 2.4 期望输出示例

以下展示成人记录的字段设计；完整提取结果应是包含成人和婴儿两条记录的列表，不能只返回此记录。
这些是待实现的领域设计，不是当前命令行输出。

```json
{
  "airline": null,
  "origin": "北京",
  "destination": "东京",
  "cabin_class": "economy",
  "passenger_type": "adult",
  "baggage_type": "checked",
  "allowance": {
    "piece_count": 1,
    "weight_per_piece_kg": 23,
    "total_weight_kg": null,
    "max_dimensions_cm": {
      "linear_total": 158
    }
  },
  "conditions": [],
  "source_text": "北京至东京经济舱成人旅客可免费托运1件行李，每件不超过23公斤，三边之和不得超过158厘米。"
}
```

同一段文字中包含多类旅客规则时，应拆分记录，不能把不同条件合并成一条。
不使用模型自报的 `confidence` 作为可靠概率；优先保留原文证据、明确的缺失值、警告与程序校验结果。
将来若实验自评置信度，必须明确未经校准，不能替代字段质量评估。

### 2.5 第一版范围

**必做闭环：**

- 以中文合成政策为主，优先处理经济舱、成人与婴儿的明确托运行李规则。
- 简单计件制与计重制，区分件数、单件重量和总重量；先使用 kg、cm 及三边之和。
- 同段的成人与婴儿规则拆分；航线等信息仅在原文明示时提取。
- 文本未提供的信息返回 `null`，不得猜测。
- Schema 校验、无效输出处理、固定评估、API 和本地基础部署。
- 无关文本、明确零额度、缺失信息等关键边界；超出当前范围的复杂条件要明确报告，不能静默套用简单规则。

**进阶扩展，不阻塞必做验收：**

- 英文与更全面的中英文覆盖。
- 手提行李、随身物品、儿童与更多舱位。
- 会员叠加、票价品牌、复杂歧义或冲突、多种规则混合。
- lb/inch 转换、尺寸长宽高拆解，保留转换依据。
- 更大的评估集、流式交互和更完整的并发/成本优化。

**本项目不纳入：**

- 图片和扫描 PDF 的 OCR。
- 自动抓取航空公司网站。
- 实时票价或订座系统集成。
- 超额行李费用计算。
- 多 Agent 协作。
- 向量数据库和 RAG。

### 2.6 推荐技术栈

- Python 3.13（当前教学与验证基线；项目要求 >=3.13）
- FastAPI
- Pydantic 2
- pytest
- httpx
- Ruff（仅在项目实际配置后使用）
- Docker
- 任意支持结构化输出的主流模型 API

模型调用应封装在独立适配器中，业务代码不要直接依赖特定供应商的响应对象。

## 4. 第一周：Python 工程基础与模型 API

### 学习目标

- 建立可维护的 Python 项目。
- 理解 LLM API 的基本调用过程。
- 完成从文本输入到模型文本输出的最小闭环。

### 学习内容

1. Python 类型标注、枚举、异常和 Protocol/ABC。
2. Pydantic BaseModel、Field、Validator 和序列化。
3. `async`/`await`、异步 HTTP 请求和并发基础。
4. System、User、Assistant 消息的职责。
5. Token、上下文窗口、Temperature 和最大输出长度。
6. API Key 的环境变量管理。
7. 超时、限流和模型服务常见错误。

### 每日安排

#### 第 1 天：初始化工程

- 安装 Python 3.13。
- 创建虚拟环境和项目配置。
- 配置 `.gitignore` 和 `.env.example`。
- 编写一个普通 Python 函数接收政策文本。
- 不在代码或测试数据中保存真实 API Key。

#### 第 2 天：第一次模型调用

- 实现最小模型调用。
- 分别记录请求开始时间、结束时间和总延迟。
- 观察 Temperature 和输出长度变化。
- 保存三组实验结果和结论。

#### 第 3 天：异步与错误处理

- 将模型调用改为异步接口。
- 配置连接超时和读取超时。
- 区分限流、认证失败、超时、服务端错误和无效请求。
- 只对明确可重试的错误进行有限次数重试。

#### 第 4 天：Pydantic 入门

- 定义行李额领域模型。
- 增加单位和非负数校验。
- 验证缺少字段、错误枚举和负数重量等场景。

#### 第 5 天：首个提取闭环

- 将模型输出解析为 Pydantic 对象。
- 对无法解析的结果返回明确错误。
- 不使用宽泛的 `except Exception` 隐藏失败。

#### 周末：复习和测试

- 编写至少 10 条单元测试。
- 整理本周术语和失败案例。
- 使用 10 段政策文本进行手工验证。

### 第一周交付物

- 可运行的命令行提取程序。
- 第一版 Pydantic Schema。
- 至少 10 条测试。
- 模型调用实验记录。

## 5. 第二周：结构化输出与领域建模

### 学习目标

- 让输出从“看起来像 JSON”升级为严格的结构化结果。
- 正确表达必做范围内的托运规则、适用条件和原文证据。

### 学习内容

1. JSON Schema 和模型原生 Structured Output。
2. Optional、Union、枚举和嵌套模型。
3. 计件制与计重制的差异。
4. 多条规则拆分。
5. 缺失信息和明确的零额度；复杂歧义与冲突作为进阶。
6. Prompt 模板、Few-shot 示例和版本管理。

### 领域模型设计要点

先实现必做范围所需字段，不一次性建完整航司领域模型：

| 分类 | 字段 |
| --- | --- |
| 航班条件 | 明示的航司、始发地、目的地；航线区域为扩展 |
| 旅客条件 | 成人、婴儿；儿童和会员等级为扩展 |
| 产品条件 | 先支持经济舱；其他舱位、票价品牌为扩展 |
| 行李类型 | 先支持托运；手提和随身物品为扩展 |
| 额度 | 件数、单件重量、总重量 |
| 尺寸 | 先支持三边之和；长宽高为扩展 |
| 附加信息 | 原文证据、明示条件；复杂例外为扩展 |
| 质量信息 | 警告、程序校验结果、Schema 版本，不把自报置信度当概率 |

不要用 `0` 代表“原文没有说明”。未提供的数据应使用 `null`，明确的零额度才使用 `0`。

### 每日安排

#### 第 1 天：完善 Schema

- 绘制领域对象关系。
- 区分 `piece_count`、`weight_per_piece_kg` 和 `total_weight_kg`。
- 定义本阶段支持的枚举、未知值及超范围处理策略，不一次性覆盖所有航司规则。

#### 第 2 天：结构化输出

- 使用模型原生 Structured Output 或严格 Tool Schema。
- 验证响应是否满足 JSON Schema。
- 禁止通过正则表达式“修复”严重损坏的 JSON 后假装成功。

#### 第 3 天：Prompt 设计

- 明确只依据输入文本提取。
- 明确缺失字段必须为 `null`。
- 明确多种适用条件必须拆分。
- 增加 3～5 个代表性 Few-shot 示例。

#### 第 4 天：多记录与缺失信息

必做测试场景：

- 成人和婴儿规则不同。
- 简单计件规则与简单总重量规则不混淆。
- 尺寸只给出三边之和。
- 原文没有说明航司。
- 明确不提供额度与未说明额度的区别。

多个舱位、会员叠加和复杂计重/计件混合为进阶，不作为本日必做。

#### 第 5 天：边界与证据

- 验证每条记录有对应原文，不把成人信息直接复制给婴儿。
- 明确 kg/cm 下的非负数和字段关系；不自行补全或推算原文未说明的额度。
- 进阶再加入英文和 lb/inch，保留原始值或转换依据，避免无法审计的单位转换。

#### 周末：扩展测试集

- 建立小型标注集，可从 20～30 条起步；数量是建议，关键是覆盖本节和第 8 节的场景。
- 标注每条样例的期望结果。
- 按来源划分开发集与固定留出集，避免近重复样例泄漏。
- 记录实际发现的模型失败并分类；没有发现时说明已测范围，不编造失败案例。

### 第二周交付物

- 稳定的领域 Schema。
- 结构化输出实现。
- Prompt v1。
- 带期望答案、覆盖标签和开发/留出划分的小型数据集。

## 6. 第三周：API、可观测性与评估

### 学习目标

- 将提取能力封装成可调用服务。
- 用指标而不是主观感受判断效果。

### 学习内容

1. FastAPI 路由、请求模型、响应模型和错误响应。
2. 同步请求与后台任务的边界。
3. 结构化日志和请求关联 ID。
4. Token、延迟和错误指标。
5. Golden Dataset。
6. 字段级 Precision、Recall、F1 和完全匹配率。
7. Prompt 与模型版本记录。

### API 建议

```text
POST /v1/extractions
GET  /health
GET  /ready
```

提取接口至少接收：

```json
{
  "text": "政策原文",
  "source_language": "zh-CN"
}
```

错误响应需要区分：

- 请求参数错误。
- 输入过长。
- 模型认证失败。
- 模型限流。
- 模型超时。
- 模型输出不符合 Schema。
- 服务内部错误。

### 每日安排

#### 第 1 天：FastAPI 接口

- 实现提取接口。
- 自动生成 OpenAPI 文档。
- 为请求长度设置合理上限。

#### 第 2 天：日志与追踪字段

每次调用记录：

- `request_id`
- 模型和版本
- Prompt 版本
- Schema 版本
- 输入字符数
- 输入和输出 Token
- 总延迟
- 重试次数
- 成功或错误类型

日志中不要默认记录完整敏感原文。

#### 第 3 天：建立评估器

至少计算：

- 整条记录完全匹配率。
- 核心字段准确率。
- 件数准确率。
- 重量准确率。
- 尺寸准确率。
- 多规则拆分正确率。
- 无依据字段的臆造率。
- 平均延迟和平均 Token。

#### 第 4 天：运行基线

- 固定模型、Prompt 和 Schema 版本。
- 对当前固定留出集运行评估，写明样本数、覆盖范围、评分规则与失败计数。
- 保存基线结果。
- 不根据测试集逐条硬编码 Prompt。

#### 第 5 天：针对性改进

- 对错误按类别聚类。
- 只选择影响最大的 1～2 类问题改进。
- 重新运行完整测试集。
- 比较新旧版本，不只展示新版本结果。

#### 周末：API 测试

- 编写 API 集成测试。
- 模拟模型成功、超时、限流和非法输出。
- 根据遗漏的失败类型扩充开发集；若调整留出集，发布新版本并保留原基线。

### 第三周交付物

- FastAPI 服务。
- 结构化日志。
- 自动评估脚本。
- 有版本和覆盖说明的评估数据。
- 第一份基线报告。

- 设置最大输入长度。

- 限制重试次数。
- 设置并发上限。

#### 第 2 天：Docker 化

- 编写 Dockerfile。
- 使用非 root 用户运行。
- 仅复制运行所需文件。

#### 第 3 天：完善测试

- 模型适配器使用 Mock，避免单元测试依赖外部服务。

- 覆盖必做范围的正常、边界与错误；扩展英文等能力后再加入对应回归。

#### 第 4 天：最终评估

- 冻结当前覆盖充分的小型留出集，不以达到 100 条作为唯一门槛。
- 运行最终版本。
- 输出成功率、字段准确率、臆造率、延迟和成本。
- 检查全部失败结果，并抽查成功结果，说明抽查数量与覆盖类别；小数据集可全部复核。

#### 第 5 天：文档

- 完善启动方式。
- 添加架构图。
- 解释 Schema 设计。
- 记录安全和隐私考虑。
- 记录已知限制。
- 使用[交付报告模板](../templates/project-report.md)说明原流程、模型必要性、收益指标和失败接管。

#### 周末：演示和复盘

- 从全新环境按 README 启动项目。
- 录制 3～5 分钟演示。
- 准备 5 分钟项目介绍。
- 总结本月最常见的三类失败。
- 依据能力验收选择下一模块，不必完成全部进阶领域规则才开始工具调用。

- Docker 化的完整服务。
- 有覆盖说明和版本的小型冻结评估集。
- 自动化测试。
- 最终评估报告。
- 项目 README 和架构图。
- 演示材料。

## 8. 评估数据集设计

### 必做覆盖矩阵

样例可以从 20～30 条起步，但数量不是验收结论。至少覆盖下面的行为，注明每类样本数、开发/留出划分及已知缺口：

| 场景 | 要验证的行为 |
| --- | --- |
| 中文简单单规则 | 件数、单件重量、总重量和尺寸不混淆 |
| 成人与婴儿多记录 | 不漏拆、不合并、不跨记录复制字段 |
| 信息缺失 | 返回 `null`，不按常识补全 |
| 明确零额度 | 不把 0 当作未知 |
| 简单计重制 | 总重量不误作单件重量 |
| 无关或无行李额文本 | 不臆造记录，按约定返回空列表 |
| 超范围或歧义条件 | 明确报告不能可靠处理，不静默输出普通成功结果 |

非法 JSON、非法数值、超时、限流等程序行为使用独立 Mock 测试，不混入模型准确率来抬高分数。
覆盖矩阵和数据数量本身不能证明模型质量；还需评分规则、固定留出结果和失败分析。

### 进阶数据集参考

增加英文、会员、单位转换等能力时，可逐步扩展至 100 条或更多，以下仅为分布参考，
不是进入下一模块的硬性要求。总数需分别说明开发集和留出集；不把所有数据都用于调 Prompt：

| 类型 | 数量 |
| --- | ---: |
| 中文简单单规则 | 15 |
| 英文简单单规则 | 10 |
| 多舱位或多旅客规则 | 15 |
| 计件制 | 10 |
| 计重制 | 10 |
| 手提行李 | 10 |
| 会员或票价品牌附加条件 | 10 |
| 单位转换 | 5 |
| 信息不完整或存在歧义 | 10 |
| 无关文本或无行李额信息 | 5 |

数据集应避免包含真实旅客姓名、票号、证件号和联系方式。使用真实航司公开政策时，应记录来源和访问日期；提交仓库前确认数据的使用与再分发条件。

## 9. 必做闭环验收标准

### 功能

- [ ] 能从中文简单托运政策提取结构化行李额。
- [ ] 能处理经济舱成人与婴儿规则，明确不支持的复杂范围。
- [ ] 能区分件数、单件重量和总重量。
- [ ] 能处理同一文本中的多条规则。
- [ ] 缺失信息返回 `null`，不凭常识补全。
- [ ] 每条结果保留对应的原文证据。

### 工程

- [ ] 所有输出均通过 Pydantic 校验。
- [ ] API 有明确的请求、响应和错误 Schema。
- [ ] 模型供应商通过适配器隔离。
- [ ] 配置和 Secret 不写入源代码。
- [ ] 超时、限流和非法输出均有测试。
- [ ] Docker 可以一条命令启动。
- [ ] 日志能通过请求 ID 串联一次调用。

### 测试与指标

- [ ] 小型标注集覆盖第 8 节必做矩阵，说明样本数和开发/留出划分。
- [ ] 在基线上明确评分规则，并在比较候选版本前登记质量门槛。
- [ ] 报告核心字段匹配、多记录拆分、无依据补充和失败计数，不预设统一准确率承诺。
- [ ] 自动化测试全部通过。
- [ ] 保存模型、Prompt、Schema 和评估集版本。
- [ ] 报告延迟、样本规模与 Token/成本；无法采集的指标明确标注，不填 0 伪装完整。
- [ ] 提供业务交付与 AI 编程协作证据，说明模拟范围和人工接管边界。

开发集与留出集、评分规则和失败计数遵循[公共验收指南](../docs/assessment.md)。
质量未达登记门槛时，写明“模型质量未通过”，不能事后降低门槛或修改答案掩盖问题；
软件功能可独立记录完成，但不能据此宣称整个模型应用已验收或达到生产标准。

### 进阶验收

完成英文、更多行李类型、会员叠加或单位换算后，为新增能力单独扩展 Schema、数据和基线。
更大数据集、P95 等统计以及更高质量目标要同时说明样本规模与业务依据，不以功能数量替代必做闭环。

## 12. 完成定义

必做闭环满足第 9 节及以下条件后可记录验收；进阶范围单独标注，不要求先覆盖所有航司政策：

1. 新开发者能根据 README 在全新环境中启动项目。
2. API 能返回经过 Schema 校验的结构化结果。
3. 自动化测试可在不访问真实模型 API 的情况下运行。
4. 真实模型冒烟测试能够按需执行。
5. 固定评估集可以重复运行并生成报告。
6. 报告质量、延迟与可采集的用量/成本；缺失指标说明原因，不声称已完成成本验证。
7. 项目明确记录限制和失败案例，而不只展示成功示例。
8. 有业务交付与协作记录；没有真实用户、真实模型或 Coding Agent 实践时如实标记未验证，不冒充对应经历。

没有模型账户仍可完成离线工程练习并继续学习后续概念，但模型质量验收必须保留“未验证”。
