# 第一个月：LLM 应用基础与航司行李额结构化提取

## 1. 本月目标

本月的重点不是构建复杂 Agent，而是掌握可靠调用大模型并将非结构化文本转换成可验证数据的工程方法。

完成本月学习后，应能够：

1. 使用 Python 调用大模型 API，并理解消息、Token、上下文窗口和采样参数。
2. 使用 Pydantic 定义结构化输出，并对模型结果进行严格校验。
3. 实现同步、异步和流式模型调用。
4. 正确处理超时、限流、网络失败和无效模型输出。
5. 使用 FastAPI 暴露服务接口，并通过 Docker 启动应用。
6. 使用 pytest 建立自动化测试和固定评估数据集。
7. 记录模型名称、请求 ID、Token、延迟和错误类型。
8. 完成一个航司行李额结构化提取程序，并用量化指标验证效果。

建议投入时间：每周 10～15 小时，共 4 周。

---

## 2. 月度项目

### 2.1 项目名称

航司行李额结构化提取程序（Airline Baggage Allowance Extractor）

### 2.2 业务背景

航空公司的行李政策通常以自然语言呈现，并受到航司、航线、舱位、会员等级、票价品牌和行李类型等条件影响。程序需要从政策文本、订单说明或客服回复中提取结构化的免费行李额和限制信息。

### 2.3 输入示例

```text
北京至东京经济舱成人旅客可免费托运1件行李，每件不超过23公斤，
三边之和不得超过158厘米。婴儿票可托运1件不超过10公斤的行李。
```

### 2.4 期望输出示例

```json
{
  "airline": null,
  "origin": "北京",
  "destination": "东京",
  "cabin_class": "economy",
  "passenger_type": "adult",
  "baggage_type": "checked",
  "allowance": {
    "piece_count": 1,
    "weight_per_piece_kg": 23,
    "total_weight_kg": null,
    "max_dimensions_cm": {
      "length": null,
      "width": null,
      "height": null,
      "linear_total": 158
    }
  },
  "conditions": [],
  "source_text": "北京至东京经济舱成人旅客可免费托运1件行李，每件不超过23公斤，三边之和不得超过158厘米。",
  "confidence": 0.98
}
```

同一段文字中包含多类旅客、舱位或行李规则时，接口应返回多条记录，不能把不同条件合并成一条。

### 2.5 第一版范围

本月纳入：

- 中文和英文政策文本。
- 托运行李和手提行李。
- 计件制和计重制。
- 成人、儿童和婴儿旅客。
- 经济舱、超级经济舱、公务舱和头等舱。
- 单件重量、总重量、件数和尺寸限制。
- 航线、票价品牌、会员等级等附加条件。
- 文本未提供的信息返回 `null`，不得猜测。

本月暂不纳入：

- 图片和扫描 PDF 的 OCR。
- 自动抓取航空公司网站。
- 实时票价或订座系统集成。
- 超额行李费用计算。
- 多 Agent 协作。
- 向量数据库和 RAG。

### 2.6 推荐技术栈

- Python 3.11+
- FastAPI
- Pydantic 2
- pytest
- httpx
- Ruff（仅在项目实际配置后使用）
- Docker
- 任意支持结构化输出的主流模型 API

模型调用应封装在独立适配器中，业务代码不要直接依赖特定供应商的响应对象。

## 4. 第一周：Python 工程基础与模型 API

### 学习目标

- 建立可维护的 Python 项目。
- 理解 LLM API 的基本调用过程。
- 完成从文本输入到模型文本输出的最小闭环。

### 学习内容

1. Python 类型标注、枚举、异常和 Protocol/ABC。
2. Pydantic BaseModel、Field、Validator 和序列化。
3. `async`/`await`、异步 HTTP 请求和并发基础。
4. System、User、Assistant 消息的职责。
5. Token、上下文窗口、Temperature 和最大输出长度。
6. API Key 的环境变量管理。
7. 超时、限流和模型服务常见错误。

### 每日安排

#### 第 1 天：初始化工程

- 安装 Python 3.11+。
- 创建虚拟环境和项目配置。
- 配置 `.gitignore` 和 `.env.example`。
- 编写一个普通 Python 函数接收政策文本。
- 不在代码或测试数据中保存真实 API Key。

#### 第 2 天：第一次模型调用

- 实现最小模型调用。
- 分别记录请求开始时间、结束时间和总延迟。
- 观察 Temperature 和输出长度变化。
- 保存三组实验结果和结论。

#### 第 3 天：异步与错误处理

- 将模型调用改为异步接口。
- 配置连接超时和读取超时。
- 区分限流、认证失败、超时、服务端错误和无效请求。
- 只对明确可重试的错误进行有限次数重试。

#### 第 4 天：Pydantic 入门

- 定义行李额领域模型。
- 增加单位和非负数校验。
- 验证缺少字段、错误枚举和负数重量等场景。

#### 第 5 天：首个提取闭环

- 将模型输出解析为 Pydantic 对象。
- 对无法解析的结果返回明确错误。
- 不使用宽泛的 `except Exception` 隐藏失败。

#### 周末：复习和测试

- 编写至少 10 条单元测试。
- 整理本周术语和失败案例。
- 使用 10 段政策文本进行手工验证。

### 第一周交付物

- 可运行的命令行提取程序。
- 第一版 Pydantic Schema。
- 至少 10 条测试。
- 模型调用实验记录。

## 5. 第二周：结构化输出与领域建模

### 学习目标

- 让输出从“看起来像 JSON”升级为严格的结构化结果。
- 正确表达不同航司政策及其适用条件。

### 学习内容

1. JSON Schema 和模型原生 Structured Output。
2. Optional、Union、枚举和嵌套模型。
3. 计件制与计重制的差异。
4. 多条规则拆分。
5. 缺失信息、歧义信息和冲突信息的处理。
6. Prompt 模板、Few-shot 示例和版本管理。

### 领域模型设计要点

至少考虑以下字段：

| 分类 | 字段 |
| --- | --- |
| 航班条件 | 航司、始发地、目的地、航线区域 |
| 旅客条件 | 成人、儿童、婴儿、会员等级 |
| 产品条件 | 舱位、票价品牌 |
| 行李类型 | 托运、手提、随身物品 |
| 额度 | 件数、单件重量、总重量 |
| 尺寸 | 长、宽、高、三边之和 |
| 附加信息 | 适用条件、例外、原文证据 |
| 质量信息 | 置信度、警告、Schema 版本 |

不要用 `0` 代表“原文没有说明”。未提供的数据应使用 `null`，明确的零额度才使用 `0`。

### 每日安排

#### 第 1 天：完善 Schema

- 绘制领域对象关系。
- 区分 `piece_count`、`weight_per_piece_kg` 和 `total_weight_kg`。
- 定义所有枚举及未知值策略。

#### 第 2 天：结构化输出

- 使用模型原生 Structured Output 或严格 Tool Schema。
- 验证响应是否满足 JSON Schema。
- 禁止通过正则表达式“修复”严重损坏的 JSON 后假装成功。

#### 第 3 天：Prompt 设计

- 明确只依据输入文本提取。
- 明确缺失字段必须为 `null`。
- 明确多种适用条件必须拆分。
- 增加 3～5 个代表性 Few-shot 示例。

#### 第 4 天：复杂政策

测试以下场景：

- 一段文本包含多个舱位。
- 成人和婴儿规则不同。
- 计件制和计重制混合出现。
- 会员可额外增加行李。
- 尺寸只给出三边之和。
- 原文没有说明航司。

#### 第 5 天：中英文与单位

- 加入英文政策文本。
- 统一 kg、lb、cm 和 inch。
- 保留原始值或转换依据，避免无法审计的单位转换。

#### 周末：扩展测试集

- 测试样例扩充到 30 条。
- 标注每条样例的期望结果。
- 记录至少 5 个模型失败案例，并分类原因。

### 第二周交付物

- 稳定的领域 Schema。
- 结构化输出实现。
- Prompt v1。
- 30 条带期望答案的测试数据。

## 6. 第三周：API、可观测性与评估

### 学习目标

- 将提取能力封装成可调用服务。
- 用指标而不是主观感受判断效果。

### 学习内容

1. FastAPI 路由、请求模型、响应模型和错误响应。
2. 同步请求与后台任务的边界。
3. 结构化日志和请求关联 ID。
4. Token、延迟和错误指标。
5. Golden Dataset。
6. 字段级 Precision、Recall、F1 和完全匹配率。
7. Prompt 与模型版本记录。

### API 建议

```text
POST /v1/extractions
GET  /health
GET  /ready
```

提取接口至少接收：

```json
{
  "text": "政策原文",
  "source_language": "zh-CN"
}
```

错误响应需要区分：

- 请求参数错误。
- 输入过长。
- 模型认证失败。
- 模型限流。
- 模型超时。
- 模型输出不符合 Schema。
- 服务内部错误。

### 每日安排

#### 第 1 天：FastAPI 接口

- 实现提取接口。
- 自动生成 OpenAPI 文档。
- 为请求长度设置合理上限。

#### 第 2 天：日志与追踪字段

每次调用记录：

- `request_id`
- 模型和版本
- Prompt 版本
- Schema 版本
- 输入字符数
- 输入和输出 Token
- 总延迟
- 重试次数
- 成功或错误类型

日志中不要默认记录完整敏感原文。

#### 第 3 天：建立评估器

至少计算：

- 整条记录完全匹配率。
- 核心字段准确率。
- 件数准确率。
- 重量准确率。
- 尺寸准确率。
- 多规则拆分正确率。
- 无依据字段的臆造率。
- 平均延迟和平均 Token。

#### 第 4 天：运行基线

- 固定模型、Prompt 和 Schema 版本。
- 对 50 条数据运行评估。
- 保存基线结果。
- 不根据测试集逐条硬编码 Prompt。

#### 第 5 天：针对性改进

- 对错误按类别聚类。
- 只选择影响最大的 1～2 类问题改进。
- 重新运行完整测试集。
- 比较新旧版本，不只展示新版本结果。

#### 周末：API 测试

- 编写 API 集成测试。
- 模拟模型成功、超时、限流和非法输出。
- 将数据集扩充到至少 60 条。

### 第三周交付物

- FastAPI 服务。
- 结构化日志。
- 自动评估脚本。
- 60 条评估数据。
- 第一份基线报告。

## 8. 评估数据集设计

100 条最终数据建议按以下比例构造：

| 类型 | 数量 |
| --- | ---: |
| 中文简单单规则 | 15 |
| 英文简单单规则 | 10 |
| 多舱位或多旅客规则 | 15 |
| 计件制 | 10 |
| 计重制 | 10 |
| 手提行李 | 10 |
| 会员或票价品牌附加条件 | 10 |
| 单位转换 | 5 |
| 信息不完整或存在歧义 | 10 |
| 无关文本或无行李额信息 | 5 |

数据集应避免包含真实旅客姓名、票号、证件号和联系方式。使用真实航司公开政策时，应记录来源和访问日期；提交仓库前确认数据的使用与再分发条件。

## 9. 最终验收标准

### 功能

- [ ] 能从中文和英文文本提取结构化行李额。
- [ ] 能区分托运行李、手提行李和随身物品。
- [ ] 能区分件数、单件重量和总重量。
- [ ] 能处理同一文本中的多条规则。
- [ ] 缺失信息返回 `null`，不凭常识补全。
- [ ] 每条结果保留对应的原文证据。

### 工程

- [ ] 所有输出均通过 Pydantic 校验。
- [ ] API 有明确的请求、响应和错误 Schema。
- [ ] 模型供应商通过适配器隔离。
- [ ] 配置和 Secret 不写入源代码。
- [ ] 超时、限流和非法输出均有测试。
- [ ] Docker 可以一条命令启动。
- [ ] 日志能通过请求 ID 串联一次调用。

### 测试与指标

- [ ] 至少 100 条冻结评估数据。
- [ ] 核心字段准确率达到 90%。
- [ ] 多规则拆分准确率达到 85%。
- [ ] 无依据字段臆造率低于 3%。
- [ ] 自动化测试全部通过。
- [ ] 保存模型、Prompt、Schema 和评估集版本。
- [ ] 报告平均延迟、P95 延迟和单次平均成本。

这些是建议目标。如果未达到，不应人工修改结果掩盖问题，而应记录失败分布、原因和下一步计划。

## 12. 完成定义

本月项目只有同时满足以下条件才算完成：

1. 新开发者能根据 README 在全新环境中启动项目。
2. API 能返回经过 Schema 校验的结构化结果。
3. 自动化测试可在不访问真实模型 API 的情况下运行。
4. 真实模型冒烟测试能够按需执行。
5. 固定评估集可以重复运行并生成报告。
6. 报告同时展示质量、延迟和成本。
7. 项目明确记录限制和失败案例，而不只展示成功示例。
