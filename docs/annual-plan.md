# 年度学习节奏参考（原始计划）

> 这是作者最初的一年学习计划，保留用于时间安排和选题参考，不代表课程已全部实现。
> 公共课程以[能力路线](./roadmap.md)和[首页课程状态](../README.md#课程状态)为准：
> 按能力验收推进，评估、安全和可观测性贯穿全程，多 Agent 为选修，
> 原计划中的月度选题不再要求各自维护一个独立应用。

这是一个为期一年的 Agent 工程师转型学习与实践仓库。

本计划面向具有传统软件开发经验的工程师，目标不是训练基础大模型，而是掌握如何将大模型安全、可靠、可评估地接入真实业务，并最终具备生产级 Agent 系统的设计、开发、测试和部署能力。

## 一年后的目标

完成本计划后，应能够：

1. 判断一个业务问题是否适合使用 Agent。
2. 设计 Agent、确定性工作流与人工审批之间的边界。
3. 使用 Python 开发和部署 LLM/Agent 服务。
4. 实现结构化输出、工具调用、状态管理和任务恢复。
5. 构建带权限控制、引用溯源和质量评估的 RAG 系统。
6. 使用 MCP 将 Agent 接入文件、数据库、代码仓库和企业 API。
7. 根据实际收益选择单 Agent、多 Agent或普通工作流。
8. 建立离线评估、回归测试、线上反馈和可观测性体系。
9. 防范提示词注入、数据泄漏和越权工具调用等风险。
10. 控制 Agent 系统的延迟、Token 使用和运行成本。
11. 完成至少 3 个作品集项目，其中至少 1 个在线运行。

### 评估、安全与生产化

## 月度项目说明

### 第 1 月：航司行李额结构化提取

从中英文航司政策中提取旅客类型、舱位、行李类型、件数、重量、尺寸和适用条件。重点学习严格 Schema、异步模型调用、错误处理、评估与 API 服务化。

### 第 2 月：代码审查助手

输入 Git Diff，返回高置信度缺陷及其位置、严重程度和修复建议。重点学习 Prompt 版本管理、误报控制以及 Precision/Recall 评估。

### 第 3 月：个人研发助理

接入代码搜索、文件读取、Issue 查询和只读数据库工具。重点学习工具契约、最大步骤数、最小权限和写操作确认。

### 第 4～5 月：企业知识库

实现中英文文档检索、混合搜索、重排序、引用、拒答、权限过滤和增量索引，分别评估检索质量与回答质量。

### 第 6 月：智能工单 Agent

完成工单分类、知识检索、信息补充、业务系统调用、人工审批和状态更新。服务重启后任务仍可恢复，写操作保持幂等。

### 第 7 月：企业研发 MCP Server

提供项目文档、代码、构建状态、Issue 和服务健康信息等工具，增加认证、授权、输出限制和审计日志。

### 第 8 月：软件需求交付 Agent

对比确定性工作流、单 Agent 和多 Agent 在成功率、成本、延迟与可维护性上的差异；只有量化收益能够证明时才保留多 Agent。

### 第 9～11 月：评估与生产化

为已有项目建立不少于 200 条的综合评估集，并补齐 Trace、监控、成本优化、安全红队测试、CI/CD 和线上部署。

### 第 12 月：作品集

整理以下三个重点项目：

1. 企业知识库 Agent。
2. 可恢复的业务流程 Agent。
3. MCP 研发助理。

每个项目应包含架构图、问题定义、技术取舍、启动方式、测试、评估报告、安全设计、运行指标、成本数据和已知限制。

## 推荐技术主线

为避免把时间浪费在重复学习相似框架上，计划采用“一条主线、按需扩展”的策略：

- 语言：Python 3.13
- API：FastAPI、Pydantic、HTTPX
- 测试：pytest
- 数据：PostgreSQL、pgvector、Redis
- Agent 工作流：选择一个主框架深入学习
- 协议：MCP 为重点，理解 A2A 的适用场景
- 可观测性：OpenTelemetry 加一个 Agent 观测平台
- 工程化：Docker、GitHub Actions

框架选择会随生态变化调整，但状态管理、工具契约、评估、安全和分布式系统可靠性是长期有效的核心能力。

## 学习节奏

建议每周投入 10～15 小时：

- 20%：阅读官方文档和理解原理。
- 60%：开发月度项目。
- 20%：测试、评估和复盘。

每周结束时回答：

1. 本周完成了哪些可运行功能？
2. 哪些测试证明功能符合预期？
3. 最常见的失败是什么？
4. 失败来自数据、Prompt、模型、Schema 还是程序逻辑？
5. 哪项改进带来了可测量的提升？
6. 延迟和成本有什么变化？
7. 下周最重要的目标是什么？

## 工程原则

1. 能用普通代码可靠完成的步骤，不交给模型自由决策。
2. 模型输出始终视为不可信输入，必须验证。
3. 先使用确定性工作流，再考虑单 Agent，最后才考虑多 Agent。
4. 不以演示效果代替固定数据集上的评估结果。
5. 任何资金、删除、权限、外部通信和代码执行操作都必须有工程约束或人工审批。
6. 每次修改 Prompt、模型、Schema、工具或工作流后都运行回归测试。
7. 同时衡量质量、延迟、成本和安全，避免只优化单一指标。
8. 优先学习稳定的工程思想，不盲目追逐框架。
