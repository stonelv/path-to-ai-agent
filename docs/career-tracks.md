# 岗位方向与作品集

[返回首页](../README.md) · [能力路线](./roadmap.md) · [招聘与技术依据](./curriculum-sources.md)

默认目标是 AI 应用 / Agent 应用工程师。以下是课程分轨建议，不是招聘统计或就业保证。
模块 00～02 提供共同起步基础；后续按路线构建一个完整系统，再依据目标职位补齐特定能力。
不同公司的岗位名称不统一，阅读实际职责比匹配职位名更重要。

## 三条方向

| 方向 | 深入内容 | 建议作品证据 | 不统一设为前置 |
| --- | --- | --- | --- |
| 应用工程（默认） | 业务需求、API/连接器、RAG、上下文、工具、交互、效果迭代 | 研发助手或工单 Agent；可演示界面/API、任务成功与失败、用户反馈或模拟评价 | GPU 调度、分布式训练、复杂平台架构 |
| Agent 平台（选修） | 运行时、队列、持久执行、多租户、权限、评估门禁、Trace、预算治理 | 把已有项目运行在可恢复的受控平台；隔离、恢复、回滚与审计证据 | 完整业务前端、全部多模态能力 |
| 推理基础设施（选修） | 模型服务、vLLM、吞吐/延迟、容量、GPU、容器编排、IaC、SLO | 对一个推理服务进行可复现负载测试，记录资源、成本、失败和容量边界 | 所有业务 Agent 模式、从零训练大模型 |

平台与基础设施岗位样本多要求既有生产经验，不能把资深岗位 JD 当成初学者统一门槛。
云账户、GPU 或付费工具不是共同起步条件；受资源限制的实验需明确写“未验证”，不把模拟结果冒充线上经验。

## 如何按已有经验选择

- 后端工程师：保留 API、数据库、队列、权限与可靠性优势，补齐模型行为、上下文与评估。
- 前端/全栈工程师：先完成应用主线，再增加流式交互、取消、进度反馈和审批界面；不要只展示聊天窗口。
- 平台/SRE 工程师：补齐最小应用与评估基础，再深入持久运行时、租户隔离、成本与运行治理。
- 对训练或算法岗位感兴趣：另行制定数学、机器学习和训练路线，本仓库不能替代该方向的基础。

## 选修如何取舍

- 多模态：应用轨可增加一个图像、文档或语音任务，分别评估输入解析和最终业务结果。
- 模型切换：应用与平台方向至少做一次同集回归；API 兼容不代表工具、结构化输出或流式语义一致。
- 微调/蒸馏：先说明现有模型、Prompt、检索或工具方案失败在哪里，再比较数据、成本和收益。
- 多 Agent：先有工作流或单 Agent 基线；只有并行、隔离或分工带来可测收益才保留。
- Coding Agent：使用与验证属于共同协作能力；开发复杂 coding harness 属于开发工具或平台方向选修。

## 作品集应该证明什么

沿用三个项目，不为每条岗位要求再创建一个应用：

1. 提取器证明模型输出能转为有证据、可验证的数据接口。
2. 研发助手证明检索、上下文、权限和工具集成能力。
3. 工单 Agent 证明审批、幂等、持久恢复、评估和交付能力。

用[交付报告](../templates/project-report.md)回答：原流程是什么、为什么需要模型、收益如何测量、
哪些情况不允许自动执行、失败由谁接管。记录真实反馈；没有用户试用时明确标注模拟评价。
不得把“完成教程”写成生产运行经历，也不以框架或 Agent 数量衡量成熟度。

## 定期校准而不是追逐职位关键词

准备投递时重新核实目标地区与经验级别的岗位原文，分清必需条件、加分项和工作职责。
记录来源、查询日期及岗位是否仍开放；不要由少量职位推算全市场占比。
现有[招聘样本](./curriculum-sources.md#招聘样本)只是 2026-09-10 的研究快照。
